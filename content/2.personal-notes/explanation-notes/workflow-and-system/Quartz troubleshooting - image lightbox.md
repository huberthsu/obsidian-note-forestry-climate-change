# 圖片全螢幕檢視功能

搭配母筆記 [[Quartz website troubleshooting report]] 一起看。這篇記錄從無到有新增全站圖片 lightbox 功能，以及後續四輪疊代修掉的互動細節 bug。

## ✅ 10.1 新增圖片全螢幕檢視功能（點擊放大、滾輪縮放、拖曳平移）

**動機**：查心智圖圖片能不能嵌進筆記/畫布時，發現網站上圖片點下去完全沒反應——不管筆記還是畫布裡的圖片都一樣，純粹是張 `<img>`，沒有裝任何 lightbox／圖片放大類的外掛。跟使用者確認範圍後決定：全站所有圖片都要有效果（不只畫布），縮放操作用滑鼠直接滾輪（不用按 Ctrl）。

**實作方式**：新增一支全站共用的 client-side script（`quartz/components/scripts/lightbox.inline.ts`）＋一份 CSS（`quartz/components/styles/lightbox.scss`），掛載方式比照網站原本就有的 popover（連結 hover 預覽）功能——在 `quartz/plugins/emitters/componentResources.ts` 的 `addGlobalPageResources()` 裡 import 進來、`push` 進全站共用的 script/CSS 清單。核心邏輯是在 `document` 上掛一個「事件代理」的 click 監聽器，只要點到的元素是 `<img>` 就開啟全螢幕檢視——不用個別修改筆記或畫布元件的程式碼，也不用動到 `vendor/canvas-page`，因為畫布裡的圖片本來就是渲染成普通 `<img>` 標籤，冒泡到 `document` 一樣抓得到。

> [!tip] 為什麼選事件代理（event delegation）而不是逐一綁定
> 全站的圖片分散在筆記內文（Quartz 核心的 markdown pipeline 渲染）跟畫布（`vendor/canvas-page` 這個獨立套件渲染）兩種完全不同的程式碼路徑，事後要嘛兩邊都要個別接、要嘛用一個掛在 `document` 上的共用監聽器靠事件冒泡統一處理。後者完全不用管圖片是誰畫出來的，新增/修改渲染邏輯也不會讓這個功能跟著壞掉。

**已驗證結果（初版）**：本地測試筆記內文圖片、畫布裡臨時塞進去的圖片，點擊都能開啟全螢幕、滾輪縮放以游標為中心正確運作、拖曳平移正常、Esc 跟點空白處都能關閉。

## ✅ 10.2 拖曳放開後方向反了、點空白處誤觸關閉——改成只有打叉/Esc 能離開

**現象**：使用者回報拖曳手感跟畫布不一樣：要放開左鍵才會平移，而且拖曳放開後畫面直接跳回外部頁面（等於被關閉了），跟畫布「按住才動、放開停在原地」的手感不同。

**排查與解決**：追出來是原本多加了一個「點空白背景關閉」的邏輯，用 `hasPanned` 這個旗標判斷「這次點擊算不算一次拖曳」，理論上拖曳後應該跳過關閉，但實際上還是會誤觸。與其继续 debug 這個判斷邏輯，使用者直接明確要求：只保留打叉按鈕跟 Esc 兩種關閉方式，拿掉「點空白處關閉」整個機制——這樣拖曳放開後不可能再被誤判成要關閉，邏輯也單純很多。移除後 `hasPanned` 這個追蹤變數也一併不需要了。

**已驗證結果**：拖曳期間即時跟著游標移動、放開後停在當下畫面不會關閉；只有打叉或 Esc 才會離開圖片。

## ✅ 10.3 加上邊界限制後，打叉按鈕壞了——`setPointerCapture()` 把 click 事件偷走了

**動機**：使用者接著要求兩件事：（1）拖曳不能超出圖片邊界（參考 Obsidian 原生圖片檢視器的手感）；（2）拖曳跟不上游標、時好時壞，要我檢查。

**解決方法**：新增 `clampPan()`，用圖片 `offsetWidth`/`offsetHeight`（物件本身在版面上的大小，不受 `transform` 縮放影響）算出目前縮放倍率下允許的最大平移量，超過就夾住——縮小到跟畫面一樣大或更小時完全不能拖（自動置中），放大時最多拖到圖片邊緣貼齊畫面邊緣。同時猜測「時好時壞」是 `setPointerCapture()` 這個 API 造成的不穩定，因為整個遮罩本來就滿版全螢幕、理論上不需要靠它來確保收得到事件，就把這行拿掉了。

**新 bug**：改完之後使用者回報打叉按鈕完全沒反應了。

**根本原因**：追出來原本拿掉 `setPointerCapture()` 是誤判——問題不是「要不要用 capture」，而是「capture 設在哪個元素上」。原本的寫法是「只要在遮罩上按下左鍵，不分按在哪，一律呼叫 `el.setPointerCapture()`」，這會把緊接著的 `click` 事件目標**重新導向**成呼叫 capture 的那個元素（`el`，也就是整個遮罩），而不是滑鼠實際點的地方。打叉按鈕是遮罩的子元素，一按下去遮罩就搶先呼叫了 capture，等放開滑鼠、瀏覽器要送出 `click` 事件時，目標已經被換成遮罩本身，打叉按鈕自己的 click 監聽器完全收不到事件。

**解決方法**：在 `pointerdown` 判斷「這次按下的起點是不是按鈕」，是的話直接跳過（不設定 `isPanning`、也不呼叫 capture），讓按鈕自己的按下/點擊照瀏覽器原生行為走；只有真的要拖曳平移時才呼叫 capture。

```js
el.addEventListener("pointerdown", (e) => {
  if (e.button !== 0) return
  if (e.target.closest("button")) return   // 讓按鈕自己的 click 正常發生
  isPanning = true
  ...
  el.setPointerCapture(e.pointerId)        // 只有真的要拖曳才 capture
})
```

**已驗證結果**：打叉按鈕恢復正常；用精確座標直接 dispatch pointer 事件測試邊界夾住的數值，跟理論算出來的最大平移量完全對上，沒有誤差。

## ✅ 10.4 拖出邊界放開後，沒按著滑鼠圖片還是會跟著跑——`pointercancel` 沒接到

**現象**：使用者接著回報：放大後想拖到邊界外確實會被卡住沒錯，但卡住之後放開滑鼠，接下來只是單純移動滑鼠（完全沒按左鍵），圖片畫面還是會跟著飄，要隨便點一下左鍵才會恢復正常。

**根本原因**：拖到邊界卡住時，圖片視覺上停了，但滑鼠還在持續移動——這種「快速、持續往同一個方向移動」的手勢，剛好符合瀏覽器判定「使用者想原生拖曳這張圖片出去」（HTML `<img>` 預設就有這種行為）的條件。一旦瀏覽器接管，就會送出 `pointercancel`（手勢被取消）取代原本該有的 `pointerup`（正常放開）。程式裡只處理了 `pointerup` 來把「正在拖曳」的狀態重設回 `false`，`pointercancel` 完全沒接，狀態就卡在「還在拖」；之後隨便一次滑鼠移動都會被誤判成拖曳中，直到下一次點擊觸發一組乾淨的按下＋放開，才會意外重設回正常。

**排查過程**：這個問題比較細，一開始懷疑是「放開時滑鼠剛好移出瀏覽器視窗外」（`setPointerCapture` 沒設好導致收不到 `pointerup`）——這確實是 10.3 拿掉 capture 那版會發生的問題，但補回 capture 之後理論上該解決了，使用者卻還是遇到。改用真的滑鼠拖曳（而非程式模擬事件）重現才注意到瀏覽器有機會用原生拖曳手勢搶走操作，才追到 `pointercancel` 這個沒接住的事件。

**解決方法**：

1. 加上 `pointercancel` 的監聽，效果跟 `pointerup` 一樣把 `isPanning` 重設為 `false`
2. 在 `pointerdown` 呼叫 `e.preventDefault()`，減少瀏覽器啟動原生拖曳手勢的機會
3. 明確把圖片的 `draggable` 屬性設成 `false`，從源頭關掉原生拖曳圖片這個行為

**已驗證結果**：改用真的滑鼠拖曳（不是程式模擬）測試：放大、刻意拖出邊界、放開、之後只是移動滑鼠不按鍵，圖片完全不會再跟著跑；打叉、Esc、邊界夾住都還正常。

> [!tip] 這次的另一個發現：拖曳殘影其實是背景沒設全不透明
> 同一輪回報裡使用者附了張截圖，畫面看起來像兩張圖疊在一起、其中一張沒跟著移動。原因是遮罩背景當時設的是 `rgba(0, 0, 0, 0.92)`，不是純黑不透明——底下真正的頁面（那張圖片本來就靜靜待在文章裡，不會跟著全螢幕檢視器一起平移）會透出 8%。使用者把 lightbox 裡的圖拖離原始位置後，底下那張「沒動」的原圖跟正在拖曳的這張疊在一起，就出現殘影的錯覺。改成純黑不透明（`#000`）就解決了，跟前面兩個 pointer 事件的 bug 是完全獨立的另一個問題。

**已驗證結果（整批）**：全部修完，commit 並 push 到 `v5` 分支（`28eff3a`）。
