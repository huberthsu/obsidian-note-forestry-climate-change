# 屬性面板與資料展示

搭配母筆記 [[Quartz website troubleshooting report]] 一起看。這篇記錄網站上屬性面板顯示筆記 metadata 的問題、Dataview 動態表格在發布後的渲染問題，以及 Bases 表格欄位顯示的問題。

## ✅ 7.1 網頁的屬性面板只顯示 `tags`，其他屬性都不見

**根本原因**：`quartz.config.yaml` 裡 `note-properties` 插件預設 `includeAll: false`，只顯示白名單裡的 `description`、`tags`、`aliases`。我的筆記大多沒有 `description`/`aliases`，只剩 `tags` 顯示得出來，不是壞掉，是預設就是這樣設計的。

**解決方法**：把 `includeAll` 改成 `true`，並用 `excludedProperties` 把 `publish`、`published`（發布日期）、`permalink`、`title`、`created`、`modified` 這些對讀者沒意義的內部欄位排除掉，只留下真正有資訊價值的屬性（`tags`、`類別`、`in`、`aliases` 等）。

> [!tip] `publish: true` 實際顯示出來的欄位名稱是 `published`
> Quartz 會把 `publish` 這個布林值轉換成一個叫 `published` 的發布日期欄位，兩個名稱不一樣，要隱藏發布日期要排除的是 `published`，不是 `publish`。

**額外發現（已在 [[Quartz troubleshooting - canvas text and portals#✅ 9.1|9.1]] 處理完畢）**：`quartz.config.yaml` 裡 `bases-page` 和 `canvas-page` 各自被註冊了兩次（一次 npm 來源、一次 `github:` 來源），build 時會跳出警告「Page frame "canvas" from canvas-page is overwriting frame from @quartz-community/canvas-page」。當時覺得沒造成明顯問題、可以晚點處理，但後來在 9.1 修 Canvas wikilink 時，這個重複註冊變成真的會擋到修復生效（見 9.1 細節），才順手一起清掉。

發布到網站後，File 那欄的連結整個斷成兩截文字，Tags 那欄則是完全空白，什麼都沒有。

**根本原因（兩個獨立問題疊在一起）**：

1. **File 欄**：`TABLE` 查詢沒有明講的第一欄，預設是 `file.link`（一個**帶別名的雙向連結**，例如 `[[路徑|顯示名稱]]`）。Quartz Syncer 發布 dataview 區塊時，是直接呼叫 Dataview 外掛自己的 `tryQueryMarkdown()` API 把查詢結果轉成 Markdown 表格文字，這個轉換**沒有對連結裡的 `|` 做跳脫（escape）**。Markdown 表格本身也是用 `|` 當欄位分隔符，連結別名前的那個 `|` 被誤判成表格分隔線，把整個儲存格切成兩半，實際發布出去的內容變成：
   ```
   | [[2.personal-notes/exam-notes/115-....md|115-....-1]] | <ul><li>#斑塊廊道基質理論</li>...</ul> |
   ```
   多出來的 `|` 讓這一列變成 3 個欄位（跟表頭 2 欄對不上），表格解析器最後只保留前兩格、把 Tags 那段內容整個丟掉，File 也被切成「路徑那半」跟「顯示名稱那半」兩個獨立文字。
2. **Tags 欄**：即使排除掉第一個問題，Tags 欄本身也有另一個獨立的坑——`file.tags` 是一個**陣列**，Dataview 序列化成 Markdown 表格時，陣列值會被轉成 `<ul><li>...</li></ul>` 這種**原始 HTML**（不是純文字），而 `obsidian-flavored-markdown` 外掛負責把 `#tag` 轉成可點擊連結的邏輯，只掃描**一般文字節點（text node）**，不會進到「html」這種節點類型裡面找 `#tag`，所以標籤永遠不會被轉成連結。

**排查過程**：

1. 直接把 git 歷史紀錄裡**真實發布過的**原始內容，複製到一篇測試筆記重新建置，實際檢查產生的 HTML，證實 Tags 那格根本沒有出現在頁面上（不是隱藏起來，是整個消失），確認問題不是憑空想像
2. 先改 File 欄，把預設 `file.link`（wikilink 格式）換成標準 Markdown 連結格式 `("[" + file.name + "](<" + file.path + ">)")`——用 `<路徑>` 角括號包住，是因為路徑裡有空格，一般 Markdown 連結語法遇到網址裡有空格會直接在空格處斷掉，要用角括號包住才能正確解析整段路徑。這樣連結本身不含 `|`，表格結構就不會被破壞
3. Tags 欄一開始以為要打開 `quartz.config.yaml` 裡 `obsidian-flavored-markdown` 外掛的 `enableInHtmlEmbed` 設定（它的作用剛好是「要不要處理塞在原始 HTML 區塊裡的 `#tag`／wikilink」）。實際打開後重新建置測試，發現**對表格儲存格內的 HTML 沒有效果**，猜測是 GFM 表格解析儲存格內容的方式跟這個設定預期的「獨立區塊 HTML」不是同一種節點類型，沒被掃到。確認沒用後把設定改回原本的 `false`，不留下沒用又有全站副作用的改動
4. 換個方向：與其想辦法讓外掛處理「HTML 裡的 tag」，不如**從源頭讓 Dataview 輸出純文字而不是 HTML**——用 Dataview 的 `join(file.tags, " ")` 把陣列轉成一般字串（例如 `#斑塊廊道基質理論 #地景生態學`）。純文字內容會走一般的文字節點解析路徑，這條路徑本來就有在處理 `#tag` 轉連結，不需要额外開任何設定。實測直接寫一篇只含這段純文字的測試表格重新建置，確認產生了正常的 `<a class="tag-link">` 連結

## ✅ 7.3 屬性面板公開顯示了一個空的 `password` 欄位

**現象**：檢查「林業碳抵換專案面臨的主要挑戰及應對障礙的方法」這篇筆記時，發現 frontmatter 裡有個空白的 `password:` 欄位，會被網站的屬性面板公開顯示出來。

**根本原因**：這個欄位是網站 `encrypted-pages`（單篇筆記密碼保護）外掛用的專屬欄位，這篇筆記本身沒有設密碼、值是空的，不是真的密碼外洩。但 7.1 把 `note-properties` 設成 `includeAll: true` 之後，凡是沒有明確排除的欄位都會被公開顯示，`password` 沒被排除，所以連這個空欄位都被公開出來，看起來很像忘記隱藏的敏感資訊。

**解決方法**：比照 `publish`／`published`／`permalink` 等既有排除項目，直接把 `password` 加進 `note-properties` 的 `excludedProperties` 清單。

```yaml
excludedProperties:
  - publish
  - published
  - permalink
  - title
  - created
  - modified
  - password
```

**已驗證結果**：本地重新編譯，該篇筆記屬性面板從 10 欄降到只顯示不含 `password` 的欄位，其餘欄位正常；commit 並 push 到 `v5` 分支（`88a7140`）。

## ✅ 7.4 屬性面板裡布林值（checkbox）欄位的打勾方塊沒有落在第二欄

**現象**：同一篇筆記的屬性面板裡，「閱讀狀態」這個布林值欄位，打勾方塊沒有正常顯示在第二欄（數值欄），而是貼在第一欄（欄位名稱）跟第二欄的分隔線上，跟其他欄位（例如 `2022`、`個人note`）的數值位置對不齊。

**排查過程**：

1. 先確認 HTML 結構本身是對的——打勾方塊確實包在正確的 `<td class="note-properties-value">` 裡，不是渲染邏輯放錯位置
2. 直接量測發現：`<input type="checkbox">` 的實際畫面座標，比它自己所在的 `<td>` 的左邊界還要**再往左 15~24px**，代表是 CSS 把它從自己的容器裡拉出去了
3. 追到 `quartz/styles/base.scss` 裡有一條全站通用的 `input[type="checkbox"] { margin-inline-start: -1.4rem; ... }`，原意是「把 Obsidian 任務清單（`- [ ] todo`）的打勾方塊往左拉，貼齊被拿掉的項目符號位置」，但選擇器沒有限定只在任務清單（`<li>`）裡才生效，導致**全站任何打勾方塊**（包括屬性面板這種布林值）都被往左拉了 1.4rem
4. 照這個理解把 `base.scss` 改成 `li > input[type="checkbox"] { margin-inline-start: -1.4rem; }`（限定只在 `<li>` 直接子層生效）後重新編譯，**打勾位置完全沒變**——代表問題不只一處
5. 進一步用瀏覽器直接列出所有選擇器裡含 `checkbox` 的 CSS 規則，才發現網站用的佈景主題套件 `@quartz-themes/core` 自己**重新刻了一整套**打勾方塊外觀（`html[saved-theme] body input[type="checkbox"]`，一次設定 39 個屬性：邊框、圓角、顏色、轉場動畫等），裡面**獨立複製了同一招**「往左拉齊」的技巧，一樣沒有限定只在任務清單生效，而且優先度比 `base.scss` 的規則更高，才是實際生效、擋住 `base.scss` 那次修正的規則

**解決方法**：

- `base.scss`：把負邊距限定在 `li > input[type="checkbox"]`，只影響真正的任務清單打勾方塊
- `@quartz-themes/core` 是外部 npm 套件、沒有原始碼可以直接改（只裝了編譯好的 `dist/`），沒辦法比照 canvas-page 直接修檔案。改在網站自己的客製化樣式檔 `quartz/styles/custom.scss`（本來就是設計給「覆蓋外掛預設樣式」用的）加一條反制規則，優先度算得比主題那條規則更高，只抵銷負邊距這一個屬性，不影響主題原本設計的邊框/顏色等外觀：
  ```scss
  html[saved-theme] body :not(li) > input[type="checkbox"] {
    margin-inline-start: 0;
  }
  ```

> [!tip] 為什麼同一個 bug 會在兩個地方各自出現一次
> `base.scss` 的規則是網站核心給「陽春」checkbox 用的基本外觀；`@quartz-themes/core` 則是佈景主題另外重畫一套更講究（有邊框顏色、圓角、跟主題配色連動）的外觀，兩者是各自獨立維護的程式碼，主題那份很可能是直接參考／複製核心那份的寫法起家，連同一個「沒限定範圍」的小失誤也一起帶過去了。之後如果還有其他「全站套用但其實只該套用在特定情境」的樣式規則出問題，也要記得檢查是不是主題套件重複定義了一份。

**已驗證結果**：本地重新編譯，屬性面板打勾方塊正確落在第二欄、跟其他數值對齊；筆記內文的任務清單打勾方塊外觀（含主題的邊框/顏色樣式）完全沒變；commit 並 push 到 `v5` 分支（`46c613f`）。

## ✅ 7.5 Quartz Syncer 發布筆記後，checkbox 的 `[ ]`/`[x]` 語法整個消失——改成唯讀

**現象**：每日任務筆記裡明明寫的是 `- [ ] 考古題筆記完成`、`- [x] 英文學習筆記完成`，發布到網站上卻變成沒有方框的普通條列文字，不是可勾選的任務清單。

**根本原因**：跟 Quartz 網站本身無關，出在**發布這個動作本身**——Quartz Syncer 外掛在把筆記推上 GitHub 之前，會用自己內嵌的 `remark`／`mdast` 解析器把整篇筆記**重新解析、重新組裝**一次（用來處理 wikilink、embed、Dataview 查詢等）。外掛編譯後的 `main.js` 裡，負責處理任務清單的 `KM()` 函式在**解析**階段有把 `[ ]`/`[x]` 從文字裡讀出來、轉成 `checked`（布林值）跟 `taskChar`（實際字元）這兩個中繼資料，但**寫回 markdown 這一步完全沒有對應的序列化邏輯**去把這兩個中繼資料轉回 `[ ]`/`[x]` 文字，資料解析出來之後就直接被丟掉，最後只剩下拿掉方框的純文字。

**排查過程**：

1. 比對 vault 裡的原始檔案跟已經同步到網站 repo 的內容，確認差異就是 `[ ]`/`[x]` 整個消失
2. 一開始懷疑是不是「checklist 後面接 Dataview 查詢」這種特殊寫法才會壞，但拿完全沒有 Dataview、單純一個 checkbox 的 `Use.md` 做對照，一樣被吃掉（連筆記裡的 `**` 都被誤判跳脫成 `\*\*`），確認是**外掛重新序列化整篇筆記**這個共通行為造成的，不是 Dataview 特有
3. 追進外掛編譯後的 `main.js`（`saberzero1/quartz-syncer`，目前安裝版本 `1.18.0`），找到 `KM()` 函式：解析時會把 `checked`/`taskChar` 寫進節點的中繼資料，但序列化（`toMarkdown`）那邊完全沒有登記對應的 handler
4. 查證 GitHub 上 `v1.18.0` 已經是目前最新版，也沒有現成的 issue 討論這個問題，但找到一個性質類似的既有 issue（`#125`，數學下標在往返序列化時被誤加反斜線跳脫），同樣屬於「重新序列化時漏處理某種語法」的通病，佐證這確實是這套外掛的已知弱點類型

**解決方法（分兩版）**：

- **第一版**：改讓 `KM()` 解析時不要把 `[ ]`/`[x]` 從文字裡拔掉，直接保留原始文字，不依賴序列化重建。測試後 checkbox 語法確實留住了，但因為段落文字開頭變成 `[`，寫回 markdown 時被 mdast 序列化器通用的「行首 `[` 可能跟連結參考定義搞混」跳脫規則抓到，自動加了反斜線變成 `\[ ]`／`\[x]`。額外實測發現：即使原始碼帶著這個反斜線，**Quartz 網站自己的 markdown 解析器仍然能正確辨識並渲染成方框**（用瀏覽器截圖確認「啟發」「用途」等筆記顯示完全正常），代表這個反斜線只是原始碼不夠乾淨，不影響最終網站呈現
- **第二版（正式修法）**：改用 GFM 官方套件 `mdast-util-gfm-task-list-item` 的標準做法——序列化時維持原本的「拔除」行為（讓 `checked`/`taskChar` 中繼資料保留，段落文字乾淨），另外新增一個 `toMarkdown` 的 `listItem` handler，在呼叫完預設的 `listItem` 序列化邏輯、拿到**已經序列化完成的字串**之後，才用字串替換的方式把 `[x] `／`[ ] ` 插進列表符號後面。因為是對已經產生好的字串做插入，不會經過會觸發跳脫規則的「文字內容」安全檢查路徑，所以不會再被加反斜線

**已驗證結果**：本地 `node --check` 語法檢查通過；重新載入外掛、重新發布後直接比對網站 repo 收到的檔案，checkbox 語法完整保留、沒有多餘的反斜線。

> [!warning] 這個修補是改 Obsidian 外掛本身，不是網站 repo，不能用 `patch-package` 固化
> 改的檔案是 `.obsidian/plugins/quartz-syncer/main.js`，屬於 Obsidian 端安裝的外掛編譯結果，跟網站 repo 的 `node_modules` 是完全不同的東西，不受這個 repo 的 `patch-package`／`postinstall` 機制保護。外掛之後如果更新版本，這個修改會被覆蓋掉，需要重新補一次；沒有簡單的自動化方式能讓這個修補撐過外掛更新。

**最終決策——把劃線效果整個拿掉，並讓網站 checkbox 改成唯讀**：

打勾任務的劃線效果會「穿透」進緊接在後面的 Dataview 表格。現象是：每日任務筆記裡「英文學習筆記完成」打勾之後，緊接在下面的表格整個被劃了一條線、文字也變成紫色。根本原因是這篇筆記的寫法是 checklist 後面**沒有空行**直接接 Dataview 查詢，Quartz Syncer 轉換表格時產生的表格區塊縮排了，會被解析成「最後一個 checklist 項目的延伸內容」，表格被巢狀進打勾任務的 `<li>` 元素裡，跟進了 `text-decoration: line-through` 的樣式。

排查過程中嘗試「只針對巢狀在打勾項目裡的表格」單獨解除劃線效果，做了三種寫法都沒真正解決（直接加 `text-decoration: none`、對每個子元素都加 `!important`、用 `display: flow-root` 強制建立新的 BFC），最後確認是 **Chromium 對「子層自己設定 `text-decoration: none` 是否真的能擋掉祖先元素畫的裝飾線」處理跟 CSS 規範預期不一致的怪癖**——子層設 `none` 沒辦法保證擋掉祖先畫的線。

於是決定：

- 採納使用者提案，把 `@quartz-themes/core` 裡 `text-decoration: line-through` 跟變色那條規則整個改成 `text-decoration: none; color: inherit`，打勾任務不再有任何文字劃線／變色效果（checkbox 本身的打勾圖示不受影響）
- 改成 `disabled: true` 讓網站 checkbox 變成唯讀，訪客看到的是 Obsidian 裡的準確狀態，點擊完全沒反應。追到 `@quartz-community/obsidian-flavored-markdown` 套件會把每個 checkbox 的 `<input>` 寫死 `disabled: false`，並搭配一段內建腳本，把使用者點擊後的勾選結果存進**瀏覽者自己那台裝置**的瀏覽器 `localStorage`（不會回寫到筆記、也不會同步給其他訪客）。改成 `disabled: true` 後點擊完全沒有反應，這段 `localStorage` 腳本也因為事件永遠不會被觸發而自然失效，不用額外處理

這兩個修改都用 `patch-package` 存成 patch 檔（`patches/@quartz-themes+core+1.1.0.patch`、`patches/@quartz-community+obsidian-flavored-markdown+0.1.2.patch`），`postinstall` 會自動套用。

> [!tip] 治本的做法：checklist 跟後面的區塊之間空一行
> 額外驗證過另一個更根本的做法（這次沒有實際採用，留給之後參考）：直接在 Obsidian 筆記裡，checklist 跟 Dataview／其他區塊之間空一行。本地重新 build 後確認 `</ul>` 會在 checklist 結束後正確關閉，表格變成完全獨立的區塊，不會再巢狀進 `<li>`。這是內容撰寫習慣的調整，跟這次 commit 的 CSS 修改是**互補、不衝突**的兩件事——CSS 修改是「不管有沒有巢狀都不會出事」的保底措施，空一行則是從源頭避免巢狀本身。

**已驗證結果**：本地 `npx quartz build --serve` 重新建置後截圖確認，原本有劃線的檔名文字、tag 標籤都恢復正常樣式，沒有任何線；用 JS 直接觸發點擊 checkbox 元素，確認 `checked` 值點擊前後沒有變化，證實唯讀生效；commit 並 push 到 `v5` 分支（`8bafeda`）。

## ✅ 7.6 Bases（`.base` 檔案）表格裡的 tags 欄位，只顯示純文字、不能點擊

**現象**：`7.bases/` 底下用 `.base` 檔案渲染出來的表格，`tags` 欄位（例如「日常」「森林經營學」）只是普通文字，跟網站其他地方（筆記內文、屬性面板）的標籤不一樣，點不下去，也沒有連到對應的 `/tags/xxx` 分類頁。

**根本原因**：跟 7.2「Dataview 表格 Tags 欄位」是完全不同的兩個套件、不同的成因，只是現象類似。網站上 `.base` 檔案的渲染是靠 `@quartz-community/bases-page` 這個獨立套件負責，跟一般筆記內文用的 `obsidian-flavored-markdown`（負責把 `#tag` 轉成連結的那套邏輯）是**兩條完全分開的程式碼路徑**，彼此互不相通。`bases-page` 內部的儲存格渲染函式 `renderCellValue()`，遇到字串型別的值一律丟給 `renderTextWithLinks()` 處理，這個函式只認得三種格式：`[[wikilink]]`、`[文字](連結)`、純網址；`tags` 欄位裡的值只是單純的字串（例如 `"日常"`），不符合任何一種格式，所以最後就照著純文字原樣輸出，完全沒有「這是標籤，要轉成標籤連結」的判斷邏輯。

**排查過程**：

1. 先確認問題不在 `.base` 檔案本身的寫法（欄位、篩選條件都正常），排除掉像 [[Quartz troubleshooting - character encoding and identifiers#✅ 3.1|3.1]] 那種「中文屬性名稱」的可能性
2. 直接找到 `@quartz-community/bases-page` 套件原始碼裡的 `renderCellValue()`／`renderTextWithLinks()`，確認裡面完全沒有處理標籤的分支
3. 比對套件安裝方式：這個套件不是像 `giscus`／`graph` 那樣裝在 `node_modules`（那些可以用 `patch-package` 修補），而是 `quartz.config.yaml` 設定成從 `github:quartz-community/bases-page` 直接 clone 原始碼、用套件自帶的 `tsup` 重新編譯，快取放在 `.quartz/plugins/bases-page`，每次 `npm install`／清快取重建都會被雲端最新版蓋掉

**解決方法**：

1. 修改 `renderCellValue()`：新增判斷「目前欄位 ID 是不是 `tags`／`file.tags`／`note.tags`」，是的話就用專門的 `renderTagValue()` 把值轉成跟網站其他地方樣式一致的可點擊連結（`class="internal internal-link tag-link"`，連到 `/tags/xxx`），5 種檢視模式（table、list、board、cards、gallery）共用同一個渲染函式，改一處全部套用
2. 因為這個套件是走 git clone＋自行編譯的安裝方式，`patch-package` 用不上。改用「整包 vendor 進 repo」的做法：把改好的套件（原始碼＋編譯後的 `dist/`）複製一份存進這個 Quartz repo 的 `vendor/bases-page/`，並把 `quartz.config.yaml` 裡的來源從 `github:quartz-community/bases-page` 改成本機路徑 `./vendor/bases-page`，這樣以後不管是 Cloudflare 重新部署還是本機清快取重建，都會直接使用這份改過的版本，不會被雲端原始版覆蓋

> [!tip] 同樣是「改第三方套件」，但跟 `patch-package`（6.1、6.2、3.3）用的不是同一招
> `patch-package` 只適合修補「裝在 `node_modules` 裡的 npm 套件」；這次的 `bases-page` 是 Quartz 特有的「git 來源外部插件」機制（設定裡寫 `github:user/repo`，build 時自動 clone＋編譯到 `.quartz/plugins/`），性質完全不同，`patch-package` 派不上用場，只能用「整包複製進 repo、改設定指向本機」這種更直接的做法。這篇跟 [[Quartz troubleshooting - properties and data display#✅ 7.7|7.7]] 是同一份 vendor 套件、同一種修法，只是修的是不同的渲染函式，彼此獨立。

**已驗證結果**：本地清掉 `.quartz/plugins/bases-page` 快取模擬全新環境重新 build，確認能正確從 `vendor/` 抓到修改過的套件並成功編譯；本機啟動預覽伺服器，使用者實際在瀏覽器確認 tags 欄位變成可點擊連結、樣式跟其他地方一致、其他欄位沒有跑版；commit 並 push 到 `v5` 分支（`7e7d01c`）。

## ✅ 7.7 Bases 表格沒寫 `order` 時，會把 `publish` 這種內部欄位也當成一般欄位顯示出來

**現象**：`1.categories/English learning notes.md` 這篇分類索引筆記嵌入了三個 `.base` 表格，其中「英文片語bases」這張表格，除了預期的 Name／Chinese translation／Tags，還多顯示了 `Publish`、`Created`、`Modified`、`Published`、`Category`、`Date`、`Title` 一大堆欄位，`publish` 這個內部發布旗標也被公開顯示出來。

## ✅ 7.9 這個套件的 `afterDOMLoaded` 腳本其實從來沒真的執行過——不只月曆，表格排序、多檢視分頁切換全部中獎

**現象**：做月曆換月按鈕時發現點了完全沒反應；回頭測試發現這個套件原本就有的功能——表格欄位點了排序、`.base` 檔案裡多個 view 之間切換分頁——同樣點了沒反應，是**做月曆之前就已經存在、只是沒人發現**的問題。

**根本原因**：`BasesBody.tsx` 是 pageType（`bases-page`）的 `body` component，不是走 Quartz 一般的 layout component 樹。負責收集全站腳本的 `quartz/plugins/emitters/componentResources.ts`，只掃描 `ctx.cfg.plugins.emitters` 底下 `getQuartzComponents()` 回傳的元件，以及 `componentRegistry.getAllComponents()` 註冊過的元件——這兩條路徑都不會經過 pageType 的 `body`。`BasesBody.tsx` 原本把 `bases.inline.ts`（負責排序／分頁切換）指派給 `Component.afterDOMLoaded`，這個屬性從頭到尾沒被任何人讀取過，是一段看起來有接上、實際上完全沒接的死程式碼。

**排查過程**：

1. 先確認腳本內容本身沒錯（`bases.inline.ts` 邏輯讀起來沒問題）
2. 用瀏覽器直接查看渲染出來的 HTML，發現頁面上根本沒有任何一個 `<script>` 標籤包含這段程式碼——不是腳本執行失敗，是**腳本從沒被放進頁面過**
3. 追進 `componentResources.ts` 的 `getComponentResources()`，確認它掃描元件的兩條路徑都不包含 pageType 的 `body`

**解決方法**：比照這個套件的 CSS 早就在用的做法——`BasesBody.tsx` 本來就是把 `<style dangerouslySetInnerHTML>` 直接內嵌進渲染出來的 HTML，不靠 `componentResources` 收集。腳本也改成同樣的內嵌方式：`BasesBody.tsx`（`.base` 檔案自己的獨立頁面）跟 `pageType.ts` 的 `renderBasesInline()`（嵌入到其他筆記裡的 base，例如這次的 exam-notes 頁面）都要各自补一份 `<script>`，兩條渲染路徑都要修，缺一個都不會生效。

> [!tip] 這個修法讓表格排序、分頁切換也「順便」修好了，但有一個限制
> 因為是內嵌 `<script>`，只有整頁直接載入（或重新整理）時才會執行；如果是從站內其他頁面用 SPA 導覽點過來（沒有整頁重新載入），腳本不會重新跑。要徹底解決要動到 Quartz 核心的外掛載入邏輯（讓 pageType 的 body component 也能被 `componentResources` 掃到），這次評估範圍太大，先不做。

**已驗證結果**：本機重新 build，確認表格欄位點了會排序、`.base` 多檢視分頁點了會切換、月曆換月按鈕點了有反應；commit 並 push 到 `v5` 分支（`8c4c391`）。

## ✅ 7.10 `vendor/bases-page` 缺建置工具鏈，而且把 `yaml` 打包進去會讓外掛在 Quartz 載入時直接掛掉

```
  at .../node_modules/yaml/dist/compose/composer.js
```

追下去發現 `yaml` 套件的 CJS 版本內部有 `require("process")`，`esbuild` 把它打包進 ESM 輸出時，會插入一段「拿不到就丟這個錯誤」的 fallback（因為 ESM 模組本來就沒有 `require` 這個全域變數）。直接用 `node -e` 單獨 `import()` 這份 `dist/index.js` 並呼叫 `BasesPage()` 不會噴錯，只有透過 Quartz 外掛載入器實際載入才會炸——確切在哪個時間點被觸發沒有完全查清楚，但推測跟 `parser.ts` 呼叫 `yaml` 的 `parse()` 解析 `.base` YAML 內容的時機有關。另外檢查了 `node_modules/@quartz-community/bases-page`（官方發布在 npm 上的版本），發現它的 `dist/index.js` 裡也有一模一樣的 `require("process")` 打包痕跡——這個問題不是這次寫的 `build.mjs` 獨有，是任何用 `esbuild`／`tsup` 把 `yaml` 打包進 ESM 輸出都可能踩到的坑，只是還沒實際驗證官方版本是不是也會在同樣的載入路徑上炸掉。

**解決方法**：`build.mjs` 把 `yaml` 加進 `external` 清單，不要打包進去，讓 Quartz 執行期用 Node 原生 `import` 去載入專案根目錄 `node_modules` 裡真正的 `yaml` 套件。同時把之前建置產生、現在已經沒人參照的舊 `chunk-*.js` 殘留檔案刪掉，並關掉 `sourcemap`（原本 vendor 進來的 `dist/` 就沒有帶 `.map`，維持一致）。

**已驗證結果**：Quartz build 不再噴 `Dynamic require` 錯誤，外掛正常載入；commit 並 push 到 `v5` 分支（`8c4c391`）。

## ✅ 7.11 月曆換月按鈕點一次跳兩個月

## ✅ 7.12 換月後新產生的筆記連結，滑鼠移過去不會跳出預覽卡片（hover popover）

**現象**：修好月曆自由換月之後，使用者反應換到別的月份時，新出現的筆記連結 hover 上去沒有跳出 Quartz 原本就有的「連結預覽卡片」（popover）功能。

**根本原因**：Quartz 核心的 `quartz/components/scripts/popover.inline.ts` 只在 `nav`／`render` 這兩個事件觸發時，才會跑一次 `document.querySelectorAll("a.internal")` 去幫每個連結掛上 `mouseenter` 監聽器，不是用事件代理（event delegation），也沒有用 `MutationObserver` 盯著 DOM 變化。月曆換月是純粹的 JS DOM 操作（`innerHTML = ""` 後用 `document.createElement` 重建），完全不會觸發這兩個事件，新建出來的連結自然沒被掃到、沒掛上 hover 監聽器。

**解決方法**：月曆每次換月重繪完 DOM 之後，主動 `document.dispatchEvent(new CustomEvent("render"))`——借用 Quartz 既有的「內容變了，請重新掃描一次」的慣例（這個事件本來就是設計給這種情境用的，只是 Quartz 核心自己從來沒有在任何地方真的發過這個事件，純粹是預留給像這次這種動態插入內容的場景）。這樣一來 popover 腳本、跟其他同樣監聽 `render` 的功能都會重新掃描一次，抓到新連結。

> [!tip] 驗證方式不夠直接，需要使用者自己再確認一次
> 用瀏覽器自動化工具模擬「滑鼠移過去」在換月後的連結上沒有成功跳出預覽卡；改用 JavaScript 直接送出 `mouseenter` 事件（`element.dispatchEvent(new MouseEvent("mouseenter", ...))`）則換月前後都能正確跳出預覽卡片，證實監聽器有正確掛上、機制本身沒問題。研判是自動化工具模擬滑鼠移動本身不夠貼近真實使用者操作（沒有連續的座標移動軌跡），不是網站的 bug，但還沒讓使用者用自己的滑鼠實際點過確認。

**已驗證結果**：程式直接觸發 `mouseenter` 事件測試，換月前後都能正確顯示預覽卡片；commit 並 push 到 `v5` 分支（`8c4c391`）。使用者實際用滑鼠操作的最終確認還沒回報。

## ✅ 7.13 月曆一開始顯示的月份，是網站「建置當下」的日期，不是訪客「當下」的日期

**現象**：7.8～7.12 都修完、實際部署上線之後，使用者從網站其他頁面點連結進到 `1.categories/exam-notes`，考古題複習日曆一開始都定格在 8/14（網站上次建置的那一天），要手動點「Today」才會跳到真正的今天。

**解決方法（第一版，範圍沒抓對）**：`calendar.inline.ts` 初始化時，比對容器上烤進去的 `data-initial-year`／`data-initial-month`，跟瀏覽器 `new Date()` 算出來的真實年月是否一致；不一致就立刻呼叫跟按「Today」按鈕完全同一個函式（`renderMonth()`），把畫面切到真正的當月，不用等使用者自己發現、自己點。本機用瀏覽器主控台故意把月曆容器上的 `data-initial-year`／`data-initial-month` 竄改成「6 月」模擬建置日期過期，重新觸發初始化後，畫面正確自動跳回瀏覽器當下的真實月份（8 月）；commit 並 push 到 `v5` 分支（`0b2b3a3`）。

**解決方法（第二版）**：乾脆放棄「比對烤進去的日期是否過期」這個判斷，改成**不管怎樣，初始化時一律用瀏覽器當下的真實時間重新呼叫一次 `renderMonth()`**，不再嘗試判斷「是否需要重繪」。多一次重繪的成本很小，換來的是「月」跟「日」都保證是瀏覽器當下的真實時間，不會再有第一版那種「範圍沒抓完整」的漏洞。

**排查過程（怎麼確定不是部署或快取問題）**：使用者一開始懷疑是沒部署到最新版或 CDN 快取，逐一排除：

1. Cloudflare 的 Version History 顯示的最新部署 commit（`5296187f`，訊息跟本機 push 出去的 merge commit一樣是「Merge remote-tracking branch 'origin/v5' into v5」，但 hash 對不上），研判是 Cloudflare 建置時自己另外做了一次 fetch+merge，屬於它内部的 git 操作，不代表接錯 repo／分支
2. 直接把本機重新編譯出來、還沒 push 的 `dist/index.js` 內容，跟 `curl` 抓下來的正式網站 HTML 裡的 `<script>` 內容做字串比對（挑一段函式呼叫的特徵字串，例如 `getFullYear()!==r||n.getMonth`），逐字相符——證實正式網站跑的就是最新版程式碼，問題出在程式邏輯本身，不是部署或快取

**已驗證結果**：本機用瀏覽器主控台把 `is-today` 手動搬到「14 號」模擬「8/14 建置、8/15 造訪、同一個月」的情境，重新觸發初始化後，反白正確校正回「15 號」；commit 並 push 到 `v5` 分支（`7a2c1e4`）。

## ✅ 7.14 7.13 的修法在正式網站上完全沒生效——真正的根本原因是「內嵌 `<script>` 不會在 SPA 導覽時執行」

**現象**：7.13 那兩版修法都 push、也確認部署到最新版之後，使用者回報網站上還是看到 8/14，怎麼樣都沒變。逐一排除了好幾個假設都排除不掉：

- 系統時鐘：確認過 Windows 右下角時鐘是 8/15，正確

**排查過程**：

1. 使用者一開始用「貼網址按 Enter」（真正整頁載入）測試，還是看到 8/14，一度誤導成「連 7.13 的修法本身都無效」的假象

3. 讀 Quartz 核心的 `quartz/plugins/emitters/componentResources.ts`，確認 popover、圖片全螢幕（lightbox）這些「不管怎麼導覽都正常運作」的功能，走的是完全不同的路：它們的腳本被收集進全站共用的 `postscript.js`，只載入一次、但會監聽每一次 SPA 導覽觸發的 `nav` 事件重新初始化——這才是內嵌 `<script>` 做不到的事

**解決方法**：把 `bases.inline.ts`（表格排序／分頁切換）跟 `calendar.inline.ts`（月曆）直接 import 進 `componentResources.ts`，比照 lightbox 的做法（`componentResources.afterDOMLoaded.push(...)`），讓它們跟 popover／lightbox 走同一條路，被打包進 `postscript.js`，在每次 SPA 導覽都重新執行一次。原本 `BasesBody.tsx`／`pageType.ts` 裡內嵌 `<script>` 的做法整段拿掉，改成單一、全站共用的來源。

> [!tip] 「改 Quartz 核心程式碼」跟「改 vendor 套件」是兩件不同重量級的事，這次選擇動核心
> 前面 7.6～7.13 全部都是改 `vendor/bases-page/`（vendored 進來的第三方套件），沒動過 Quartz 核心（`quartz/` 資料夾）本身。這次是評估過風險後第一次直接改核心檔案（`quartz/plugins/emitters/componentResources.ts`），因為「pageType 的 body component 沒有正常管道接進全站腳本收集機制」這個缺口，只靠改 vendor 套件本身修不掉——vendor 套件不管怎麼寫，都沒辦法讓自己的腳本被 Quartz 核心正確收集。這算是這次踩過最深的一個坑，值得記住：不是所有問題都能靠 vendor 一路修到底，有些缺口真的要動到框架本身。

**順便修到的第二個獨立 bug**：追蹤這個問題的過程中，發現「嵌入到筆記裡的 base」（例如考古題複習日曆嵌在 exam-notes 這篇筆記裡）的渲染路徑（`pageType.ts` 的 `createBasesCodeblockTransform`），組出外層 `<div>` 的屬性時寫成 `node.properties = { class: "bases-page bases-inline" }`，完全沒帶 `data-initial-view`。`bases.inline.ts` 的分頁切換腳本讀不到這個屬性時，會 fallback 成 `page.dataset.initialView || "0"`，永遠預設抓第一個 view 當作啟用中的分頁，跟伺服器端算好的「該顯示哪個 view」對不上（這也是先前「怎麼一下子是 table、一下子是 calendar」看起來很不穩定的部分原因）。修法：讓 `renderBasesInline()` 把算好的 `initialIndex` 一併回傳給呼叫端，正確設進 `data-initial-view`。

**已驗證結果**：本機用「先進首頁、真的點連結」模擬使用者平常的瀏覽情境（不是貼網址），全程用真的滑鼠點擊＋螢幕截圖親眼確認（不只信任程式回傳的 DOM 資料）：8/15 正確反白、換月按鈕點一次動一個月（August ⇄ July）、Today 按鈕正確跳回今天；commit 並 push 到 `v5` 分支（`627a479`）。

## ✅ 7.15 為了讓月曆換月後 hover 預覽正常，借用了全站共用的 `render` 事件，結果把 dark mode 開關搞壞了——而且只有嵌了 Bases 的頁面才會壞

**現象**：7.14 上線後，使用者回報「考古題筆記」這頁沒辦法切換 dark mode，其他頁面都正常。點擊左上角的 dark mode 開關完全沒反應（畫面不變）。

**根本原因**：這是 7.14 那次修法自己造成的副作用，不是新的獨立問題。7.14 為了讓月曆換月後新產生的筆記連結也能 hover 出預覽卡片，在 `calendar.inline.ts` 的 `renderMonth()` 裡加了一行 `document.dispatchEvent(new CustomEvent("render"))`，想借用 Quartz 元件本來就會監聽的 `render` 事件，讓 popover 腳本重新掃描一次新連結。問題是：`render` 這個事件在這次改動之前，整個 Quartz 核心從來沒有任何地方真的 dispatch 過（純粹是各元件寫好、等著被使用的預留事件），所以所有監聽 `render` 的元件，寫的時候都預設「這輩子最多只會被叫到一次」，完全沒有防重複初始化的保護。第三方套件 `@quartz-community/darkmode` 的初始化函式也監聽 `render`，每次被呼叫都會重新對「.darkmode」按鈕 `addEventListener("click", ...)` 一次，而且監聽器函式是每次呼叫時在函式內部重新宣告的（閉包），跟前一次呼叫掛上去的不是同一個函式參照，`addEventListener` 不會自動去重——所以掛了兩個獨立的 click 監聽器。點一次按鈕，兩個監聽器依序觸發：第一個把主題從深色切成淺色，緊接著第二個又把它從淺色切回深色，兩次抵銷，畫面完全沒變化，跟按鈕壞掉一樣。只有嵌了 Bases（月曆／表格）的頁面會觸發這個 `render` dispatch，其他頁面完全不受影響，所以症狀才會是「只有這頁壞掉」。

**排查過程**：

1. 先在瀏覽器主控台檢查 `localStorage.getItem("theme")` 跟 `<html>` 上的 `saved-theme` 屬性，發現點擊前後這兩個值完全沒變——證實不是「畫面沒更新但狀態有變」，是真的整個切換邏輯沒生效
2. 對照測試：在首頁（沒有月曆）點同一顆按鈕，正常切換；回到考古題筆記頁再點，狀態卡住不動——鎖定問題跟這頁「有月曆」這件事有關
3. 找到 `node_modules/@quartz-community/darkmode` 編譯後的原始碼，讀懂它监聽 `nav`／`render` 兩個事件、每次觸發都重新對 `.darkmode` 按鈕掛一次 click 監聽器、完全沒有防重複的邏輯
4. 直接在主控台監聽 `render` 事件並計數，確認月曆每次 `renderMonth()`（包含網頁一載入就會跑的第一次）都會多 dispatch 一次——搭配「按鈕會累積多個監聽器、點一次觸發偶數次等於沒反應」這個機制，完全對得上症狀

**解決方法**：不要再共用 `render` 這個廣播式事件，改成發一個範圍窄、只有 popover 腳本會聽的專屬事件 `bases-content-inserted`（在 `quartz/components/scripts/popover.inline.ts` 裡額外註冊一個監聽）。同時讓 popover 自己的 `setupPopovers()` 也做防重複初始化（用 `WeakSet` 記錄已經掛過監聽器的連結），這樣就算之後這個事件被觸發好幾次也不會有副作用。`darkmode` 套件本身完全沒動——它是純 npm 套件，沒有 vendor 進來，改不了，這次的修法完全繞開它，不需要碰它。

> [!tip] 這個 bug 給的教訓：全站共用事件只要「借用」就有風險，因為你不知道還有誰在聽
> `nav`／`render` 這類廣播式事件的設計前提，是每個監聽者都各自負責防重複、彼此互不影響。但實際上 Quartz 核心好幾個元件（至少 darkmode 確認過）並沒有做這層保護，因為在這次之前 `render` 從沒被真的觸發過，等於從沒被驗證過「重複觸發會怎樣」。以後任何時候想要「借用」一個看起來閒置、沒人在用的共用事件，都要假設監聽端沒有防重複保護，最安全的做法是自己開一個新事件，不要跟其他元件共用同一個廣播頻道。

**已驗證結果**：本機用真的滑鼠點擊＋螢幕截圖確認：dark mode 在考古題筆記頁能正常雙向切換（深→淺、淺→深），换月後新出現的 17 號筆記 hover 仍然能正確跳出預覽卡片（深色模式下樣式也正常）；commit 並 push 到 `v5` 分支（`a025096`）。

## ✅ 7.17 很多筆記的 graph view 都連到不相關的 bases 頁面

**現象**：使用者回報很多筆記的 graph view 會連到不相關的 `.base` 頁面。具體例子是「邊緣效應對不同區域碳貯存量的影響」這篇筆記（tags 是 邊緣效應／碳儲存／碳核算，跟碳抵換機制完全無關，筆記本身也沒有嵌入任何 `.base`），local graph 卻連到「外加性bases.base」「永久性bases.base」「碳抵換bases.base」「碳抵換品質標準bases.base」這四個主題完全不相干的 base 頁面。

**根本原因**：`vendor/bases-page/src/pageType.ts` 的 `generate()` 幫每個 `.base` 檔案建立「虛擬頁面」時，算這個虛擬頁面的 `links`（graph／backlinks／content-index 都是拿這個欄位當連結資料）是這樣呼叫的：

```ts
links: resolveBasesEntries(basesData, allFileData, undefined, basesSelfContext)
  .entries.map((e) => e.slug as SimpleSlug),
```

第三個參數 `view` 寫死傳 `undefined`。而 `resolver.ts` 的 `resolveBasesEntries()` 有兩層過濾：先套用最上層的 `basesData.filters`（不管有沒有傳 `view` 都會套用），再套用 `view?.filters`（**只有真的傳了 `view` 進去才會套用**）。問題出在：像「外加性bases.base」「永久性bases.base」這幾個檔案，篩選條件只寫在 `views:` 底下的某個 view 裡，**沒有寫在最上層的 `filters:`**：

```yaml
views:
  - type: table
    filters:
      and:
        - file.tags.contains("外加性")
```

`view` 是 `undefined` 時，第二層（也是唯一有寫的那層）過濾整個被跳過，等於完全沒有過濾，直接把全站所有筆記（當時 73 篇）都塞進 `links`。因為 Quartz 的 local graph 是雙向畫邊（A→B 或 B→A 任一方向存在就畫線），所以「base 頁面反過來連到每一篇筆記」在每篇筆記自己的 graph 上都會顯示成一條邊，看起來就是「連到一堆不相關的 bases」。

**沒壞的對照組**：像「卡片盒筆記bases.base」「外掛與功能說明bases.base」「考古題筆記bases.base」等，篩選條件是寫在最上層 `filters:`（例如 `category.contains(link("Zettelkasten notes"))`），不受這個 bug 影響，本來就是對的——這也是為什麼使用者會發現「有些 base 反而連得很準」，兩種寫法在 Obsidian 裡都合法，純粹是這支 vendor 程式碼漏掉了其中一種情況。

**排查過程**：

1. 本地 clone 落後 origin/v5，先 `git pull` 抓到目標筆記所在的最新 commit
2. 確認目標筆記的「相關筆記bases」heading 底下是空的，筆記本身沒嵌入任何 `.base`，排除「筆記自己連錯」的可能
3. 在 `pageType.ts` 找到虛擬頁面 `links` 的生成邏輯，發現 `resolveBasesEntries()` 的 `view` 參數寫死傳 `undefined`
4. 讀 `resolver.ts`，確認 `view?.filters` 這層過濾只有在有傳 `view` 時才生效，`basesData.filters`（最上層）則無論如何都會套用
5. 逐一檢查 `content/7.bases/*.base`，分成兩組：篩選寫在最上層 `filters:` 的（不受影響）vs. 只寫在 `views:` 裡的（外加性／永久性／碳抵換／碳抵換品質標準，這四個真的壞了）
6. 用 `git stash` 切換「修復前／修復後」兩個版本各自完整 `quartz build` 一次，直接讀 `public/static/contentIndex.json` 比對每個 `.base` 虛擬頁面 `links` 陣列的長度與內容，量化確認差異（見下）

**解決方法**：把虛擬頁面 `links` 的算法改成「對 `basesData.views` 裡的每一個 view，各自呼叫 `resolveBasesEntries(basesData, allFileData, view, basesSelfContext)` 拿到套用過該 view 篩選條件的結果，再把所有 view 的結果做聯集（union，用 `Set` 去重）」，取代原本直接傳 `undefined` 的寫法。選聯集不選交集，是因為同一個 `.base` 檔案的多個 view 通常代表「同一批資料的不同呈現方式」（例如同一份資料一次用 table 看、一次用 calendar 看），不是層層縮小範圍的過濾器；目前這個專案裡每個 `.base` 都只有一個 view，聯集/交集結果一樣，只有以後真的加多 view 時才會有差。改完 `src/pageType.ts` 後，用 `vendor/bases-page/build.mjs`（無 `tsup`，esbuild 腳本，見 7.10）重新編譯 `dist/index.js`。

**已驗證結果**：`git stash` 切換前後兩版分別完整 build，比對 `contentIndex.json`：

| base 檔案 | 修復前 links 數 | 修復後 links 數 |
|---|---|---|
| 外加性bases.base | 73（=全站所有筆記） | 2 |
| 永久性bases.base | 73 | 3 |
| 碳抵換bases.base | 73 | 4 |
| 碳抵換品質標準bases.base | 73 | 2 |
| 卡片盒筆記bases.base（本來就對） | 15 | 14 |
| 考古題筆記bases.base（本來就對） | 5 | 4 |

修復前那四個壞掉的 base，`links` 裡都包含目標筆記（不相關）；修復後都不再包含。另外也用本機 `--serve` 開瀏覽器實際打開目標筆記頁面（`/2.personal-notes/zettelkasten-notes/the-impact-of-edge-effect-on-carbon-storage-in-different-regions`），確認 local graph 畫面上不再連到那四個不相關的 base；commit 並 push 到 `v5` 分支（`2117d38`）。
